01
Principles
How we think about AI
01 · Principles

Six things we agree on

  • Human accountability — a person decides and signs off; whoever ships it owns it.
  • Verify, then trust — run the code, check the facts, confirm packages exist.
  • Data protection is the hard boundary — the one rule we never bend.
  • Least privilege for AI tooling — deny secrets by default, grant access deliberately.
  • Same bar as human work — same review, tests and security scanning.
  • Transparency — honest about AI's role, internally and with clients.
02
Sensitive Data
The hard boundary
02 · Sensitive data

The golden rule

Assume it's kept

Anything you send to a public AI tool may be retained, logged, or used for training. Only an approved tool with a no-training / zero-retention term changes that. When unsure, treat it as public.

Policy Client terms & NDAs override this — check per project.
02 · Sensitive data

Classify before you share

PUBLIC

Open source, published docs, marketing. Any tool is fine.

INTERNAL

Generic non-sensitive material. Approved business-tier tools — not free tiers that train on inputs.

CONFIDENTIAL

Proprietary logic, architecture, financials. Approved enterprise tools only, minimized/redacted.

RESTRICTED

Client code under NDA, secrets, PII. No AI without written client approval.

02 · Sensitive data

Handle it safely

Never paste into AI

  • Passwords, API keys, tokens, .env files
  • Client source / databases under NDA
  • Personal data (PII), payment or health data
  • Trade secrets & proprietary algorithms

Do this instead

  • Keep secrets in a secret manager, referenced by env
  • Redact — placeholders for real names, keys, IDs
  • Reproduce bugs with minimal synthetic data
  • Scan before commit with gitleaks
03
Guardrails
Make the safe path the default
03 · Guardrails

Don't rely on memory — enforce it

Two layers in Claude Code, committed to the repo so every engineer and every AI session inherits them.

  • Permissions — declaratively deny reading .env, keys and secrets/**.
  • Hooks — a PreToolUse hook blocks risky commands; a PostToolUse hook scans edits for secrets.
// .claude/settings.json — the cheapest guardrail
"permissions": {
  "deny": ["Read(./.env)", "Read(./.env.*)", "Read(./secrets/**)"]
}
03 · Guardrails

What we enforce

  • Block secret access — AI can't read or print env / key files.
  • Block destructive commands — no rm -rf on home, no force-push to main.
  • Scan on every edit — gitleaks runs after writes; a hit stops the commit.
  • Least privilege for agents & MCP — grant only the tools a task needs.
Why Safety becomes "the tool won't let you," not "everyone remembers."
04
Coding With AI
Ship with confidence
04 · Coding with AI

AI writes the first draft.
You are the engineer.

The moment you commit it, it's your code — same responsibility, same review, same standard as if you'd typed every line.

04 · Coding with AI

Non-negotiables

  • Understand before you commit — can't explain it, don't ship it.
  • Review for security — injection, authz, unsafe defaults, secrets in code.
  • Verify dependencies are real — AI hallucinates packages; attackers weaponize the names.
  • Own the tests — don't let the model grade its own homework.
  • Same PR review — AI-generated changes get no fast lane.
04 · Coding with AI

Where to lean in — and hold back

Strong fit

  • Boilerplate, scaffolding, migrations
  • Test drafts, docstrings, READMEs
  • Refactors on code you understand
  • Explaining errors & unfamiliar code

Keep human-led

  • Core architecture & design
  • Security-critical logic & payments
  • Anything touching Restricted data
  • Final sign-off on correctness
05
When Things Leak
The runbook
05 · When things leak
Rotate, don't just delete

A secret that reached a remote, a log, or any tool is compromised permanently — assume it was scraped in seconds. Deleting the file or rewriting history does not fix it. Rotation is mandatory. Cleanup only stops future exposure.

05 · When things leak

The runbook, in order

1
Contain

Disable or scope down the credential now; revoke its sessions.

2
Rotate at source

New key first, deploy it, then revoke the old — don't down prod.

3
Assess exposure

Check provider audit logs & billing for unauthorized use.

4
Purge history

git filter-repo / BFG, force-push, team re-clones.

5
Report

Tell your lead / security immediately — not a blame event.

6
Prevent

.gitignore, secret scanner, deny-list + hooks, secret manager.

The whole policy, one screen

Do / Don't

Do

  • Own, review and verify every output
  • Use approved tools with training off
  • Redact & use the secret manager
  • Check per-project client rules
  • Rotate & report leaks immediately

Don't

  • Paste secrets or .env into AI
  • Feed NDA client code to unapproved tools
  • Ship code you don't understand
  • Trust facts, sources or packages blindly
  • Blame the AI — you're accountable
Before you start using AI

Your setup checklist

  • Approved AI tools on your company account training & history off
  • Shared guardrails installed .claude deny-list + hooks, pre-commit gitleaks
  • Secret-manager access verified so you never hard-code or paste secrets
  • Project AI rules confirmed with your lead what's allowed, what's off-limits
  • Security contact saved rotate & report fast if something leaks
